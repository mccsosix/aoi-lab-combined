## 1. 项目背景与本次输入

AOI LAB 的 FOV 工具当前内置：

- 相机：1,135 台
- 镜头：426 款
- 当前镜头品牌：燦銳、視清

本次新增两份输入资料：

- `lenses(1)(2).json`：用户结合官方网站补充后的新镜头数据库
- `lens-extraction-report(1)(2).json`：新镜头数据库的提取与校验报告

后续 AI 应在现有 AOI LAB 源码基础上合并新资料，不要另起一个项目，也不要直接用新 JSON 覆盖前端运行数据后就结束。必须同步修改标准化脚本、字段模型、校验脚本、测试、说明文档和最终两个 ZIP。

## 3. Lens Resolution 当前问题与修正方案

### 3.1 已确认的根因

当前 426 款镜头的原始资料中：

| 数据情况 | 数量 | 当前表现 |
|---|---:|---|
| 有 `image_mtf_lp_mm_min` | 270 | 可以计算并显示 |
| 有 `object_space_resolution_um` | 56 | 当前没有接入，错误显示为 `—` |
| 两项都没有 | 100 | 应显示资料缺失 |

目前项目只把 `image_mtf_lp_mm_min` 映射为 `imageMtfLpMmMin`，遗漏了原始数据库中已经存在的 `object_space_resolution_um`。修正后，旧 426 款镜头中可显示镜头解析度的数量应由 270 增加到 326。

合并新文件后，623 款镜头至少可明确获得：

- MTF：273 款
- 直接物方解析度：56 款
- 两项均无：294 款

不得给这 294 款批量填入猜测值。

### 3.2 数据模型修改

在镜头类型中新增可选字段：

```ts
objectSpaceResolutionUm?: number | null;
resolutionSource?: "manufacturer-object-space" | "mtf-estimate" | null;
```

标准化脚本增加：

```ts
objectSpaceResolutionUm: item.object_space_resolution_um ?? null
```

`resolutionSource` 可以在生成前端记录时写入，也可以由报告层动态判断。

### 3.3 显示优先级

报告中的 `Lens Resolution` 必须按以下优先级：

1. 有厂家直接物方解析度 `objectSpaceResolutionUm`：
   - `Lens Resolution = objectSpaceResolutionUm / 1000`
   - 单位显示 `mm`
   - 详情注明“厂家物方解析度”
2. 没有直接值，但有镜头像方 MTF：
   - 按当前项目约定：`1 / (2 × MTF lp/mm × 实际倍率)`
   - 详情注明“基于像方 MTF 的物方 half-pitch 估算”
3. 两者都没有：
   - 主报告显示 `—（资料未提供）`
   - 不允许显示成 `0`
   - 不允许根据 NA、光圈、像素数或相似型号猜测

注意：厂家直接给出的物方解析度本质上不是 pixel，因此建议将主报告单位从当前的 `mm/pixel` 改成 `mm`，或者保留用户的报告模板格式但在详情中明确说明口径。不要把相机 Resolution 与镜头光学解析度混为一项。

### 3.4 指定记录回归测试

至少增加以下测试：

- `XF-10MDT044X110-1C`：原始资料存在 `object_space_resolution_um: 12`，应显示 `0.012 mm`。
- `DTCM110-80H-AL`：存在 `image_mtf_lp_mm_min: 135`，0.208× 时按 MTF 公式得到约 `0.018 mm`。
- `XF-10MDT035X110-1C`：当前交接资料没有 MTF，也没有直接物方解析度，应明确显示资料未提供，不能自动填用户以前报告里的 `0.015 mm/pixel`，除非后续取得可靠来源并记录 source。

## 4. DOF 新字段兼容

新镜头 JSON 增加了：

```text
depth_of_field_min_mm
depth_of_field_max_mm
```

后续 AI 必须保留这两个字段。建议类型为：

```ts
depthOfFieldMinMm?: number | null;
depthOfFieldMaxMm?: number | null;
```

报告仍遵循用户已经确认的项目口径：

```text
报告 DOF = 镜头资料 DOF × 实际倍率
```

处理规则：

- 单值 `depth_of_field_mm`：沿用现有计算。
- 有 min/max：分别乘以实际倍率，显示范围，不要先求平均值。
- 不要再用“存在 `depth_of_field_aperture`”自动判断 DOF 一定是 `±`；是否为正负范围必须依据原资料的符号、min/max 语义或明确元数据。
- 缺失 DOF 时显示资料未提供。

## 5. Sensor Size 与 FPS 问题

### 5.1 当前 FPS 覆盖情况

当前 1,135 台相机中：

| 品牌 | 总数 | 有 FPS | 缺 FPS |
|---|---:|---:|---:|
| Basler | 462 | 462 | 0 |
| 海康机器人 | 641 | 639 | 2 |
| 度申 / Do3think | 32 | 0 | 32 |
| 合计 | 1,135 | 1,101 | 34 |

因此，很多 `fps=—` 的直观原因是：当前页面默认第一台相机来自度申，而 32 台度申记录全部缺 FPS。当前度申原始 JSON 本身没有其他可恢复的帧率字段，不是前端漏掉了同一份 JSON 中的其他 key。

海康缺 FPS 的两款为：

- `MV-CT032G-38GM01-MAX-35L-WBC`
- `MV-CT050G-24GM01-MAX-16L-WBC`

### 5.2 `12.58M / fps=—` 的实际含义

例如度申 `M3ST1209M-H-O2C`：

- 分辨率：4096 × 3072
- 程序计算像素：12.583 MP
- `nominalMegapixels`：缺失
- `sensorFormat`：缺失
- `fps`：缺失

当前报告在标称像素缺失时直接回退到 `resolutionWidthPx × resolutionHeightPx / 1,000,000`，所以显示成 `12.58M`。这只是分辨率计算值，不是厂家标称“12.58M”，也不是真正的 Sensor Size。

### 5.3 后续数据补充任务

后续 AI 应优先从厂商官方资料补齐 34 台相机，重点是 32 台度申：

- `fps`
- `nominalMegapixels`
- `sensorFormat`
- `sensorModel`
- 必要时复核传感器宽高、像元尺寸和接口

资料优先级：

1. 对应型号官方产品详情页
2. 官方 PDF / 产品手册
3. 官方系列目录
4. 用户提供的公司资料

不得：

- 从型号中的数字直接猜 FPS
- 从同系列相似型号复制 FPS
- 用接口带宽理论值代替厂家帧率
- 用第三方商城参数覆盖官方参数而不注明来源

每个补充值应保留来源 URL/文件名、获取日期和是否为最大满分辨率帧率。若资料同时给彩色/黑白、不同位深或 ROI 帧率，只采用默认满分辨率条件，并在 notes 中保留条件差异。

### 5.4 报告显示优化

建议把目前一行：

```text
Sensor Size：12.58M / fps=—
```

改为来源透明的显示：

```text
Sensor Size：12.58 MP（按分辨率计算）/ 靶面规格待补 / fps=待补
```

有完整资料时仍可简洁显示：

```text
Sensor Size：25M（1.1″）/ fps=14
```

显示规则：

- 有 `nominalMegapixels`：显示厂家标称值。
- 仅有计算像素：必须加“按分辨率计算”或“约”，不得伪装成厂家标称值。
- 有 `sensorFormat`：放在括号中。
- 无 `sensorFormat`：显示“靶面规格待补”，不要省略到让用户误以为 `12.58M` 就是 Sensor Size。
- 无 FPS：显示 `fps=待补` 或 `fps=—（资料未提供）`。
- 技术详情继续显示传感器物理宽 × 高和对角线；兼容判断仍使用毫米对角线，不使用 `1″` 字符串排序。

## 6. 镜头新数据库合并要求

### 6.1 保留原始输入

建议将用户新提供的 `lenses(1)(2).json` 与 `lens-extraction-report(1)(2).json` 作为新版上游资料归档，不要手工复制 623 条记录到前端 JSON。

标准化脚本应兼容新文件根结构：

```json
{
  "schema_version": "...",
  "generated_at": "...",
  "source_archive": "...",
  "source_policy": "...",
  "lenses": [],
  "summary": {}
}
```

### 6.2 合并与 ID 策略

- 使用 `brand + model` 作为业务去重键。
- 已存在的 426 款应保持现有稳定 `id`，防止用户 IndexedDB 中的自定义、隐藏状态失联。
- 197 款新增记录可采用新文件自带 ID，但必须先做全库唯一性校验。
- 同品牌同型号只保留一条，别名放入 `aliases`。
- 保留所有 `source_files`、`notes`、`data_quality`、`conflicts`。
- 内置资料升级时，继续遵守当前 IndexedDB 规则：未被用户自定义的记录升级；用户已经修改的记录不得被新版默认值覆盖。

### 6.3 推荐状态

不要因为官网来源就自动标为 compatible 或 verified。自动推荐至少需要：

- 有实际倍率或可用倍率范围
- 有最大像圈
- 有明确接口
- 无关键字段冲突

新增的 188 款官网表格记录缺少接口，应继续为 `manual-review`，但仍可在组合计算中显示数学结果，并提示人工确认。
