## 0. 结论先行

> **当前状态（2026-09-29）**：P0 尖刺 ✅、**P1 已交付 ✅**、**P2a 打光影像骨架 ✅**、**P2b 图片·画圈·拖拽已交付 ✅** —— 06 在工具箱里可用：主页第 6 张卡片 → 四段表单（封面 / 需求 / 工站 + 站内打光影像段（含画布）/ 生成）→ 生成并下载 pptx。工站与影像页都可增删，页序由 `planPages()` 算出，图片上传即降采样、拖拽调位、拖出红圈。**P2c（工站环境小图）/ P3a（需求页）/ P3b（结论页）/ P4（存档）待做**。实现详情见 **§9.5 / §13 / §14**，报告结构口径见 **§12**。

1. **值得做，而且比想象的容易。** 这份报告里**没有图表、没有 SmartArt、没有 OLE、没有表格**——12 页只有 4 种元素：文本框、矩形/椭圆、直线/箭头、图片。生成端不需要一个通用 PPTX 引擎，只需要拼装这 4 种。
2. **【2. 硬體設定】整页是 100% 可算的**，而且**算它需要的字段现有 FOV 工具已经全有了**（取证见 §3）。这是投入产出比最高的一块。
3. **【3. 打光影像】那 7 页是"自动化价值最高但最难"的一块**——图上信息只有人知道，但**排版、编号、画红圈、页数伸缩**完全可以交给工具。**建议这一块做交互，不做 AI 识别。**
4. **技术路线推荐「模板占位符化 + 浏览器端 OOXML patch」**，不是从零生成。理由见 §4.1。这条路 100% 保真（母版、字号、红色标注、光路图都在），工作量约为从零生成的 1/5，且能塞进现有的单文件离线版（`offline/index.html`）。
5. **不要做的一件事**：不要"在原始 pptx 上按 shape 名字改文字"。这份文件里 shape 名重复且简繁混杂（同一页出现 4 个 `文本框 43`、`图片 8`，另有 `文字方塊 48` / `圖片 1` / `图片 37` / `参数 36` 混用），按名字定位必然改错地方。

### 1.1 六个结构发现（决定了方案怎么设计）

1. **全篇只有 4 种绘图元素**（`sp` / `pic` / `cxnSp` / `graphicFrame`，其中 `graphicFrame` 只用来做 0 个表格）。→ 生成端不需要通用引擎。
2. **同一套"页面骨架"重复 12 次**：蓝色标题条 `AutoShape 107`，固定 `(0, 0)` 尺寸 `201.2 × 45.1 pt`；正文块 `文字方塊 48`，固定 `(19.8, 45.1)` 宽 `527.4`。→ 骨架可以完全固化成模板。
3. **没在用版式（slideLayout）**：12 页里 8 页挂在 `slideLayout1/5`，只有 2 页挂在 `slideLayout4/8`——说明作者是**直接在新空白页上摆框**，不是套版式。→ 我们也不必套版式，直接固化成模板页即可。
4. **`slide4` 是 `slide3` 复制后缩放粘贴的证据**：`slide4` 的 `组合 2` 组内子元素坐标被压成 `0.9 / 0.6 pt` 这种量级（组内局部坐标）。→ 印证现有流程就是"复制上一页 → 改数字"，这正是我们要替掉的手工活。
5. **红圈是独立椭圆 shape，不是画在图上的**：`椭圆 12/13/14/15…` 每页 2–10 个，坐标独立。→ 可以做成"拖拽画圈"交互，导出成可编辑 shape（比现在的手工贴圈更好用，还能对齐像素）。
6. **`slide2` 的尺寸标注混了两种做法**：大部分红线框是画在 CAD 图纸图片里的（不可拆），但 `6.7±0.03` 是独立文本框。→ 需求页只能"半自动"，别指望全自动。

> **P2a 补充（2026-09-29）**：第 2 条要打个折 —— 骨架确实每页都有，但**不是一套**：工站页的正文块宽 527.4pt，影像页是 527.4（普通）/ **577.9**（特殊，说明框更宽）。所以模板里留了**两个影像壳**而不是一个。第 5 条的红圈已确认在删除范围内（影像壳只留标题条 + 名称/说明框，见 §13.3）。

## 2. 字段级清单：固定 / 可算 / 必填

这是整个功能的核心。**"可算"的比例决定这个工具值不值得做。**

### A 类 — 可自动计算（不需要人输入，只需选型）

| 字段 | 出现在 | 计算口径（已实测验证） | 数据来源 |
|---|---|---|---|
| `FOV` | slide3/4 | `sensorWidthMm / magnification` | 设备库 ✅ |
| `Resolution` | slide3/4 | `FOV / resolutionWidthPx` | 设备库 ✅ |
| `Lens Resolution` | slide3/4 | `1 / (2 · MTF · M)` 或衍射极限 `1.22·λ·F#/M` | 设备库 / 镜头规格 ✅ |
| `DOF` | slide3/4 | **`标称DOF × 40%`** ← ★与现有代码口径不一致，见 §3.2 | 设备库 ✅ |
| `Sensor Size` | slide3/4 | `{标称MP}M / fps={fps}` | 设备库 ⚠️ fps 有出入 |
| 光路图距离标注 | slide3/4 | `工作距离` / `玻璃厚` / `环光间距` | 设备库 + 部分需人填 |
| 公差帶 | slide3/4 | `2 × 最小公差` | 图纸数据 |
| 理想系統解析度 | slide3/4 | `公差帶/10 ~ 公差帶/8` | 推导 |
| 选型结论句 | slide3/4 | `選用{N}M Camera {彩色/黑白}相機 + {M}x 遠心鏡頭可符合產品需求` | 模板句 |
| 验证结果计数 | slide12 | `{n}吋產品:共{k}種密封圈打光及外觀驗證-{OK/NG}` | 需求页数据 |
| 页码 / 母版 | 全部 | 由 PPTX 自带的 `sldNum` 占位符自动出 | 模板 |

**实测验证链（slide 3，可复现）**：
```
MV-CH250-90UC  → 5120×5120, sensor 12.8×12.8mm   [cameras.json 命中]
DTCM110-80H-AL → mag 0.208, DOF 14.8mm, WD 228mm  [lenses.json 命中]

FOV        = 12.8 / 0.208        = 61.54 mm      ← 报告写 61.54 ✚
Resolution = 61.54 / 5120        = 0.01202 mm/px ← 报告写 0.01202 ✚
DOF        = 14.8 × 0.40         = 5.92 mm       ← 报告写 ±5.92 ✚
光路图 "228"                      = WD 228mm      ← 报告标注 228 ✚
公差帶      = 2 × 0.08           = 0.16          ← 报告写 0.16 ✚
理想解析度  = 0.16/10 ~ 0.16/8   = 0.016~0.02    ← 报告写 0.016~0.02 ✚
```
**7 项全中。** 这一页是真的可以一键出。

## 3. 与现有工具箱的接口（这块是白捡的）

### 3.1 文字格式已经 1:1 对齐

`src/fov/domain/report.ts` 的 `formatReportText()` 产出的前 7 行，与 slide3 的 `文字方塊 14` **格式逐字符一致**（`CCD：` / `Sensor Size：` / `Lens：` / `FOV：` / `DOF：` / `Resolution：` / `Lens Resolution：`）：

```
formatReportText() 产出                      slide3 实际
CCD：MV-CH250-90UC                           CCD： MV-CH250-90UC(新增)
Sensor Size：25M（1.1"）/ fps=14             Sensor Size：25M/ fps=14.3
Lens：DTCM110-80H-AL                         Lens ： DTCM110-80H-AL
FOV：61.54 × 61.54 mm                        FOV：61.54*61.54mm
DOF：±5.92 mm（±14.8 mm × 0.208）            DOF：±5.92mm (±14.8mm*40%=5.92mm)
Resolution：0.01202 mm/pixel                 Resolution：0.01202mm/pixel
Lens Resolution：0.018 mm/pixel              Lens Resolution：0.02mm/pixel
```
→ **不重写计算逻辑**。P1 的实际做法：06 直接调 03 的 `calculateFov()` + `lensResolutionMm()`（`src/fov/domain/`），**只把"排版/连接符/小数位"这套报告格式写在 06 的 `domain/spec.ts` 里**（`×`→`*`、`Lens ： ` 全角冒号、Resolution 5 位小数、`trim()` 抹尾随 0）。数字来自 03、格式来自 06，两边不重复实现算法 —— **复制算法就会漂移**。

### 3.2 ★ DOF 口径冲突（**已裁定：40% 通用规则**，2026-09-28）

| 出处 | 公式 | 对工站页的取值 |
|---|---|---|
| 现有代码 `report.ts` | `dofSourceMm × magnification` | 14.8 × 0.208 = **3.08 mm** |
| 打光报告实际写法 | `dofSourceMm × 40%` | 14.8 × 0.40 = **5.92 mm** ✅ 与报告一致 |

**裁定结果**：40% 是**本厂通用折减规则**，做成 `DEFAULT_DOF_DERATE = 0.4`（`domain/spec.ts`）。
**关键边界**：这条只加在 **06 侧**，**不改 03 的公式** —— 03 仍是"× 倍率"。两边数字不同是**故意的**，不是 bug，别"顺手统一"。括号里的说明按报告格式写成 `(±14.8mm*40%=5.92mm)`。

### 3.3 可以直接借的其它东西

- `src/fov/data/cameras.json`（1147 台）+ `lenses.json`（426 款）→ 相机/镜头选型下拉，不用新建。
- FOV 工具的 IndexedDB 设备库（`src/fov/storage/db.ts`）→ 06 可以复用同一份用户自定义设备。
- `src/lib/utils.ts` 的 `toSimplified()` → 报告是繁体、工具箱是简体，**生成时统一转繁**（源文件全繁：`檢測/內徑/毛邊/破損/乘坐`）。

- `src/lib/chart-injector.ts` 是"OOXML 级注入"的先例 → **06 的 PPTX patch 用同一套路数**，团队已有认知基础。

## 4. 技术方案

### 4.1 三条路线对比

| | A 从零生成 PPTX | **B 模板占位符 + OOXML patch（推荐）** | C 服务端 python-pptx |
|---|---|---|---|
| 保真度 | 低（45pt 标题条、实心红框、3D 光路图都要重画） | **100%** | 高 |
| 工作量 | 大：手写 `sp`/`pic`/`cxnSp` 的 XML + 坐标换算 | **中**：一次性做模板，运行时只做字符串替换 + 图片替换 | 中 |
| 母版/页码/FOXCONN 徽标 | 要重建母版 | **自带** | 要重建 |
| 可离线单文件 | ✅ | ✅（模板 base64 内嵌，约 400 KB） | ❌ 破坏"双击即用"交付模型 |
| 用户后续在 WPS 里手改 | 可以但版式陌生 | **可以，就是原版式** | 可以 |
| 风险 | 版式永远对不上，团队不接受 | 模板漂移（解法见下） | 需要服务器 |

**选 B。** 关键取舍：这条路把"排版难题"一次性冻结进模板，把运行时的复杂度压到极低。

### 4.2 一次性预处理：怎么做出 `lighting-report-template.pptx`

用脚本（Node 或 Python，跑一次，产物入库到 `src/lighting-report/assets/`）对一份**脱敏副本**做 5 件事：

1. **正文块单 run 化 + 占位符化**：把 `文字方塊 14` 这种块里的每个 `<a:p>` 整段替换成单个 `<a:r>`，文字改成 `{{ccd1.spec}}`，`rPr` 保留第一个 run 的样式。→ 运行时就是纯字符串替换，**彻底绕开"一句话被切成 7 个 run"的经典坑**。
2. **图片打标**：把要替换的 `pic` 的 `cNvPr name` 改成 `{{IMG:defect.0}}`；固定图（相机 3D 图、光源实物图）保持原样不动。
3. **可重复页标记**：在打光影像页的 `slideN.xml` 里插一个自定义属性 `<p:cSld name="{{REPEAT:defect}}">`（或写进 `docs/` 的页索引 JSON），运行时时按需克隆 N 份。
4. **清理**：删 12 个空的 notesSlide、清 `docProps`、删本案专属媒体（28 张图里只保留 4 张模板资产：`image6.png` 相机镜头 3D / `image7.jpeg` 相机机身 / `image8.png`+`image9.png` 光源条）。
5. **冻结版本**：模板文件加 `template-version.json`（源报告 sha256 + 预处理脚本版本），**改模板必须走一次重跑**，避免手改模板导致占位符与代码对不上。

> 预处理后模板预计 **150–300 KB**（现在 5367 KB 里绝大部分是本案照片）。

### 4.3 运行时生成管线（浏览器内，**P1 / P2a / P2b 已全部实现**）

```
表单 / 03 报告文本带入 / 人工覆盖 / 上传图片（已在 UI 侧降采样为 JPEG dataURL）
        ↓
  ReportModel (JSON，单一真相源；图片只留降采样后的 dataURL，原图不入模型)
        ↓
  planPages()  ← 算出最终页序（封面 → 需求 → [工站 → 本站影像…] → 結論）
                 + 每页的图片、版式、排版告警                    ✅ P2a/P2b
        ↓  validate + 单位换算（繁简由「转繁体」按钮显式触发，不隐式转换）
  ① JSZip 加载模板                                    ✅ P1
  ② 逐页：按 key 做单 run 字符串替换（XML 转义 + 多段拆分 + 红字规则）  ✅ P1/P2b
  ③ 按需克隆重复页（复制 slideN.xml + rels + 注册 4 处）    ✅ P1
  ③b 用不到的壳**先删**，再按 plan 分派 part（首次用占本体、之后克隆）  ✅ P2a
  ③c setSlideOrder() 一次性重写 sldIdLst = 页序唯一权威       ✅ P2a
  ④ 图片字节约写进 ppt/media/，跨页按 dataURL 去重；本页 rels 挂 image 关系  ✅ P2b
  ⑤ 红圈椭圆 shape 注入（图片相对归一化坐标 → 页面 pt → EMU）  ✅ P2b
  ⑥ 删掉未使用的页（工站数 < 需求页时）                   ✅ P1（模板已归一化为 6 个壳）
  ⑦ 重新打包 → Blob → 下载                             ✅ P1
        ↓
  .pptx （可用 WPS / PowerPoint 打开继续手改）
```

> **P2a 的核心变化：页序从"插页时凑下标"改成"先算数组、再一次性重写"**。
> `planPages()` 产出一个 `PlannedPage[]`，每页只声明「用哪个壳 / 填哪些 token / 标签」；
> 具体落到哪个 part 是 `generate.ts` 的事。这样工站增删、缺陷组增删、单页增删都只影响这个数组，

### 4.5 重复页克隆的注意事项（**已实现**，代码在 `domain/surgery.ts`）

- 每克隆一页要新增 3 处注册：`ppt/_rels/presentation.xml.rels`、`ppt/presentation.xml` 的 `<p:sldIdLst>`（`id` 从 256 起且不重复）、`[Content_Types].xml`。**再加第 4 处**：`docProps/app.xml` 的幻灯片计数（含 HeadingPairs 向量）——少任何一处 WPS/Office 就会挑刺。P1 已全部实现并门禁覆盖。

- 克隆页的 `notesSlide` 关系一律不复制（模板已删空备注）。
- ✅ **修正 P0 的误判（P2a 已实测推翻，见 §12.6）**：源报告里的 `Page:3` / `Page:4` / `Page:12` **是版式里的 `sldNum` 域，不是静态文本**。把影像壳重排到第 5 位后，LibreOffice 渲染出来的页脚自动变成 `Page:5`。所以**页序 = `sldIdLst` 的顺序，页码自动跟随** —— 克隆与重排都不需要回写页码。门禁 H 段断言"没有任何一页把 `Page:N` 写成静态文本"，I 段再用 LibreOffice + pypdfium2 独立复核真页数。

### 尖刺暴露出来的坑（教训，别忘）

| 坑 | 现象 | 解法 |
|---|---|---|
| **JSZip 3 的 `.asText()` 已移除** | `This method has been removed in JSZip 3.0` | 一律 `await zip.file(n).async('text')` |
| **`文本框 43` 一页出现 4 次** | 按 shape 名定位必然改错 | 一律按 `cNvPr id` 定位（模板间 id 稳定） |
| **一句话被切成 6+ 个 run** | 直接替换文字会掉 `(新增)` 的红色 | 预处理阶段压成单 run；红色改由运行时 highlight 规则重建 |
| **`rPr` 自闭合 vs 成对两种写法** | 想在自闭合 `<a:rPr .../>` 上加子元素会写出非法 XML | `applyProps()` 统一转成成对形式再插 `solidFill`；属性走 `b="1"`，子元素顺序 fill → latin |
| **`spAutoFit`** | 占位符只有 1 行时框会缩短 | 不影响：anchor 是 top，展开后自动长回原高度 |
| **数字格式** | `±14.80mm` / `0.0200mm` 与源报告的 `±14.8mm` / `0.02` 不一致 | 定小数位后抹尾随 0（`trim()`），不要裸 `toFixed` |
| **窄公差带下「理想系統解析度」退化成废话** | 公差 ±0.05 → 带宽 0.1 → 1/10=0.01、1/8=0.0125，固定 2 位小数打出 `0.01~0.01mm` | 两端都用 4 位 trim。门禁有断言 |
| **压单 run 会丢手动配色** | 模板预处理只留**第一个** run 的 `rPr` → 后半段 `FF0000` 消失 | 颜色规则从「没有才加」改成**覆盖**（`setRunColor`）+ 按 token 语义化高亮（`TOKEN_RULES`） |
| **验证脚本自身的坑** | 按 `<a:t>` 取行会被红色 run 切断；按前缀过滤会命中光路图上的固定标签 | 黄金样本必须按**段落**取行，并按「连续 N 段」定位 |
| **克隆页的标题条宽度会跟着模板页走** | slide3 的蓝条 201pt、slide4 是 382pt；克隆页继承 201pt → 长标题溢出、红字落到白底看不见 | 见 §9.5「标题条宽度模型」 |

### 归一化模板：6 个壳 + 运行时克隆（P1 时是 1 张工站页，P2a 扩到 6 个壳）

### 标题条宽度模型（P1 踩到、P2a 重标定 —— 必须记住的坑）

源报告两条标题条的宽度是**人手拖的**，而且**拖得并不整齐**：slide3 短标题条 201.2pt，但实测文字墨迹只到 190.7pt（**最后一个字就被裁掉了**）；slide4 长标题条 382.0pt，文字墨迹 200.0pt 结束（条子拖得比字宽一倍）。克隆时继承模板页的宽度 → 长标题会溢出蓝条（红字落到白底看不见）。

解法：`layout.ts` 用**字符宽度模型**估算所需宽度。系数是用 LibreOffice 渲染实测反解出来的（把条宽强制拉到 700pt、量真实墨迹像素）：

- CJK 字符 `0.9417em`、拉丁字符 `0.6173em`、空格 `0.30em`
- 估算宽度 = 上述加权和 **+ 条子左右内边距 14.17pt（`lIns`+`rIns` = 90000 EMU 各侧）+ 8pt 安全余量** → `TITLE_BAR_PADDING_PT = 22.17`
- 超页宽时封顶到 `720pt − 4pt` 并打 `capped` 标记（只告警，不自动缩字）

**口径是"不裁切"，不是"等于源稿"**：源稿本身就在裁字，所以生成物允许比源稿宽（≤12%），但**永不超过文字实际墨迹**。门禁 G 段断言：2 个源稿样本（201.2 / 382.0pt）、2 条实测墨迹（207.3 / 200.0pt）、内边距、系数、封顶、以及"按内容改写后第 4 页比第 3 页宽"。

**只改字号不改条宽的思路是错的** —— 源报告本身不缩字，只拉条。

### 工站增删 + 03 带入（回应 §11 的两个拍板）

- **工站可增删、起码 1 个**：UI 里 `+ 添加工站` / 删除（剩 1 个时按钮禁用）/ 上移下移。每张卡片可填相机、镜头、光源 ×2、检测项目，并带 `datalist` 自动补全（读 03 的设备库）。

- **不做 Excel 批量入口**（用户裁定）。

### 12.6 页码不是静态文本（P2a 实测，推翻 P0 的误判）

- 推论：**页序的唯一权威就是 `sldIdLst`**；`setSlideOrder()` 一次性重写它即可，**没有任何"回写页码"的工作**。

## 14. P2b 交付结果（2026-09-29，已完成）

**一句话**：影像页从"只有标题与说明的骨架"变成"真的能贴图、能画圈、能拖着调位置"，并且**与源报告逐页核对过**（红圈位置、说明文字、红字强调全对上）。

### 14.1 一个画布引擎，三处复用（§12.4 的落地）

| 文件 | 职责 | 关键点 |
|---|---|---|
| `domain/canvas.ts` | **坐标 → OOXML 图形的唯一转换处** | `picXml` / `ellipseXml` / `insertShapes` / `autoLayoutImages` / `aspectFit` / `resolveSlotBoxes` / `circleBox`。纯函数、零 I/O，所以 Node 门禁直接用 |
| `image-io.ts` | **只跑在浏览器**：读文件 → 降采样 → JPEG dataURL | canvas / `createImageBitmap` 是浏览器独有的，所以"阈值"留在 domain（`IMAGE_MAX_PX = 1600` / `IMAGE_JPEG_QUALITY = 0.82`），"像素操作"放这里 |
| `ImagePageEditor.tsx` | 单页的画布 + 图片清单 | 拖拽/画圈的监听挂在 window（只注册一次），状态走 ref —— 挂在 state 上会每帧重建监听器，拖动会断 |

**为什么必须程序生成而不是克隆**：源报告 7 页影像页是**纯人工摆的、没有网格**（slide05 的 4 张图在 `(48,304)(462,171)(292,174)(26,171)`，slide09 的 5 张图各不相同），且红圈是**独立的 `椭圆` shape 而不是烘焙进图片**。所以图片与红圈只能由程序生成；模板里只有「标题条 `AutoShape 107`」和「名称/说明框」可克隆。

### 14.2 坐标一律用 pt，红圈用「图片相对归一化」

- 画布上写进 style 的百分比，分子就是 domain 算出的 pt（`pct(v, 720)`），**不存在第二套换算**。
- 红圈的 `x/y/w/h` 是**相对所属图片自身**的归一化框，所以重排图片（自动摆放或手拖）时圈自动跟着走，不需要重算。
- spTree 顺序固定为**先所有图片、后所有红圈**（源报告 slide5 就是这个次序）。反过来圈会被图盖住 —— 肉眼很难发现、导出后一定不对，门禁 J 段与 E2E 各断言一次。

### 14.3 自动摆放 + 拖拽微调（用户 2026-09-29 拍板的形态）

- 默认**自动摆放**：`gridShape(n)` 挑行列让格子尽量接近方形，再用 `aspectFit` 在格内等比缩放居中。
- **拖过任何一张图 → 整页切手动，并把当时所有图的位置固化**（否则松手后其余图会跳）；点「重新自动摆放」回到自动。
- 手动页里新加的图回落自动格位，并给一行提示（可能重叠）。
- 单页上限 12 张（`MAX_IMAGES_PER_PAGE`）、图片区下限 140pt（说明写太多会被压到下限并告警）。

### 14.4 上传即降采样（现场图 4000×3000，不压会把报告撑爆）

- 长边 > 1600 才压，**本来不超的不放大**。E2E 用真文件验证：2400×1800 → 1600×1200，800×1200 原样。
- PNG 先铺白底再编码 —— 直接转 JPEG 会把透明区变黑。
- 同一张图跨页复用按 dataURL 去重，只写一份 media；选号按**基名**（`imageN`）判重，避免出现 `image1.wmf` + `image1.jpeg` 这种同基名双后缀。

### 14.5 顺带查清/修掉的三件事

1. **`planPages` 算出的告警以前被丢掉**（空图页 / 图超量 / 图片区被压扁 / 手拖出页外）。这些是"生成了但结果不对"的主要来源，现在并入 `GenerateResult.warnings`。
2. **名称行默认值误用了标题条前缀**：原来给的是 `3.打光影像-破損`，而源报告的名称行是 `打光影像-破損`（章节号只属于标题条）。已拆成 `IMAGE_SECTION_PREFIX` / `IMAGE_CAPTION_PREFIX` 两个常量。
3. **名称行结尾的 `-特殊` 是红加粗**（源报告 slide8/slide11 实测 `FF0000` + `b="1"`），属于结构性标记 → 按文字自动重建。

### 14.6 说明里的红字：`**…**` 约定

源报告两页特殊影像的说明里有手涂红字（slide8「輕微NG無法看出」、slide11「需要改善乘坐」）。自由文本没法靠规则猜，于是约定 **`**文字**` = 红加粗**（与 `(新增)` 同语义），**标记本身不会印进 PPT**（`HighlightRule.trim = 2`）。

- 画布预览上就渲染成红字（`ImagePageEditor` 的 `markInline`），**与 domain 的 `TOKEN_RULES` 同一口径**，不是各写一套。
- 唯一与源稿的偏差：slide8 那处源稿是**红但不加粗**，这里统一成红加粗。要纯红可在 WPS 里去掉加粗。

### 14.7 这一版的量化结果

| 产物 | 页数 | 影像页 | 图片 | 说明 |
|---|---|---|---|---|
| `lighting-2stations-replica.pptx` | 12 | 7 | 15 | **与源报告同构**：图片位置、红圈、说明、红字全部照搬（源报告 16 个 pic 里有 1 个是跨页复用同一张媒体，去重后 15） |
| `lighting-1station.pptx` | 6 | 2 | 4 | 1 工站 + 1 组 2 页（两种壳各用一次） |

> 复刻样张与源报告的**页序不同**是设计使然：源报告把两张工站页都排在影像页之前，本工具按用户拍板改成「工站与其影像段紧邻」。所以复刻样张的 `Page:4` 对应源报告的 `Page:5` —— 页码是 `sldNum` 域，跟着 `sldIdLst` 走，本来就是对的（§12.6）。

## 15. P2c 交付结果（2026-09-30，已完成）—— 需求页能填 + 逐工站需求推导 + 模板族注册表

### 15.1 触发这轮的三条用户反馈（原文口径）

> 1 封面后应该接的是检测需求；2 产品需求不一定是外径和内径，这里可以填写公共的比如公差，
> 相机像素也不用在需求这里，应该在工站那里根据型号识别出，这里还有一个 PPT 可以参考。

第 ① 条经实测是**认知偏差**：产物第 2 页本来就是 `1.檢測需求`（页序 `封面 → 1.檢測需求 → 2.硬體設定-CCD1 → … → 4.結論`）。
真问题是**需求页的内容填不了**（模板带着上一个案子的 4 张产品照，界面上也没有输入口）。

### 15.2 数据模型：三段各归各

| 段 | 老模型（P2b 及以前） | 新模型（P2c） |
|---|---|---|
| 【1.檢測需求】页 | 无（固定页，带源报告照片） | `RequirementSpec = { lines: string[]; image: UploadedImage \| null }` —— **一行行手打的项目名称 / 公共条件，或一张品保发的需求表图** |
| 工站页右上「需求推导」 | 全报告共用一份 `ProductRequirement`（外径 / 厚度 / 最小公差 / 相机像素 / 彩色） | **逐工站**：`requireLead`（自由前置行）/ `toleranceMm` + `toleranceStyle`（`pm` ｜ `band`）/ `inspectNote` / `lensKind` / `colorCamera` / `requireOverride`（整块覆盖）；相机像素按本站 `cameraModel` 从设备库认 |
| 相机像素 | 需求段手填一个数字 | **从工站相机型号识别**（`Camera.nominalMegapixels`）；型号不在库则留空并告警 |

**用户 2026-09-30 明确**：需求页不是字段体系（「产品需求不一定是外径和内径」），公共条件（公差）也是**手打文字**。

### 15.3 需求推导的自动规则（`spec.ts` 的 `buildRequireLines(station, cam, mag)`）

```
① [可选] station.requireLead                        ← 自由前置行，留空不出行
② [有公差才有] 最小公差±0.08mm，公差帶=0.16          ← style='pm'（数值是 ± 值，带宽 = 2×）
              最小公差帶 0.1mm                      ← style='band'（数值就是带宽）
   [值可跟 inspectNote]                              ← 例：一次檢測1pcs，伺服控制相機左右移動拍兩次
③ [有公差才有] 理想系統解析度=1/8~1/10  → 0.016~0.02mm
④ 選用25M Camera彩色相機 + 0.208x 遠心鏡頭可符合產品需求
```

- **没有公差**：跳过 ②③；若有 `inspectNote` 则它单独成一行（源报告 CCD4 那种「檢測範圍：一次量測2pcs產品」）。
- **`requireOverride` 非空**：**完全不自动生成** —— 参考报告里有超出任何模板的写法，整块手写。
- 逐字符真值：源报告 slide3（CCD1）/ slide4（CCD2）都是这 4 行，只有倍率 0.208 / 0.209 不同。B 段断言逐字符比对。

### 15.4 模板族注册表（`domain/template-layout.ts`）

一族 = 一份预处理过的模板 pptx + 一组壳 + 一组版式约定。生成端只认开关，不认具体是哪份报告：

| `imageHeader` | `section` → 影像页标题条写 `3.打光影像-{缺陷}` | `station` → 标题条写工站名（`1.硬體配置-CCD1`） |
| `imageCaptionPrefix` | `打光影像-` | 空（名称行整条由用户填） |
| `hasConclusion` | `true` | `false`（实测那份**没有**結論页） |
| `requireImageBox` | `{20, 92, 680, 386}` pt | 待定 |
| `stationHeaderPrefix` | `2.硬體設定-` | `1.硬體配置-` |

UI 顶部已有**版式选择器**（`TemplatePicker`，注册表驱动，加一族不用改组件）。
门禁 K 段用一份**临时造的族对象**验了 `imageHeader: 'station'` 与 `hasConclusion: false` 两条开关真的被 `planPages` 认。

> ⚠️ **四合一族为什么还没做**：那份报告的 4 张工站页是**四种不同版式**（CCD1 / CCD2 / 3D雷射 / CCD4，
